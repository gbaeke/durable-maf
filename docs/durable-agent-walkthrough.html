How the durable report agent survives a crash

A step-by-step tour of worker.py (the orchestration version), client.py and demo.sh. Shared pieces now live in report.py. The workflow version and the two agent versions at the end cover only what's different. For each step: what the code does, why it is built that way, and what has to be in place for it to work. The replay stepper further down walks through a real run in which the worker was killed on section 3.

TL;DR

  • What it is: a report-writing agent on Microsoft Agent Framework's Durable Extension (GA), running against the local Durable Task Scheduler emulator, with Luna behind agentgateway. ./demo.sh kills the worker on section 3 and a new worker finishes the job.
  • How durability works: every checkpoint is recorded in the scheduler's history. After a crash, the new worker replays that history and continues at the first unfinished step. Finished model calls come from the record and are not repeated.
  • Four versions, one setting (MODE=…):
    • orchestration: we wrote the steps as Python code.
    • workflow: the same steps as an Agent Framework workflow graph.
    • agent: one agent with tools decides the steps itself, but its whole tool loop is a single checkpoint.
    • durable-tools: the same agent, with a checkpoint after every model call and every tool call, like Dapr Agents.
  • What a crash costs: only the interrupted step runs again, except in agent mode, where the whole agent run restarts (12 model calls instead of 8). Steps can run twice, so they must be safe to repeat.
  • Watch out for:
    • The scheduler caps each stored item at 1 MB. The writer's conversation and the workflow's event log keep growing.
    • Agents that use tools need the Responses API, because Luna rejects tools on Chat Completions.
    • durable-tools relies on one private function of the extension, so keep the package version pinned.
The moving parts

Who talks to whom

The worker holds no state you can't afford to lose. Everything that matters lives in the task hub inside the emulator: the orchestration's event history, the agents' conversations (stored as durable entities), and the queues of pending work. Any worker that connects to the same task hub can carry on.

Reading the dashboard

What you see at localhost:8082

The dashboard is a window onto what the scheduler has stored. It runs nothing itself. A few words first, assuming no prior knowledge.

Scheduler

The service that stores durable state and hands out work. Here that's the emulator in Docker, shown as emulator in the breadcrumb at the top.

Task hub

One named, isolated box of state inside a scheduler, like a database inside a database server. Ours is durable-maf. Workers and clients only see the hub they connect to. Everything under the TASK HUB heading on the left is about the hub you selected.

Instance

One run of something. Every ./demo.sh creates one orchestration instance, plus three agent entities.

Entities

A durable entity is a small, named object whose state is kept by the scheduler and changed only by messages sent to it, one at a time. Agent Framework stores every agent session (one conversation) as an entity. That's what the screenshot shows. Explained row by row below.

Agents

The same entities, shown the Agent Framework way: per agent, its sessions and the conversation inside them (prompts, replies, tool calls). It's a preview feature. Switch on Enable Agent pages in the gear menu at the top right if it's empty.

Schedules

Orchestrations that start automatically on a timer, like a cron job ("run this report every morning"). This demo starts runs by hand, so the page is empty.

Workers & Metrics

Which worker processes are connected right now and how much work flows through the hub. During demo.sh you'd see worker #1 disappear and worker #2 appear. When no worker runs, nothing gets processed, but nothing is lost either.

Configuration

Settings for this task hub and the dashboard. The emulator has few options; in Azure this is where hub settings live.

Entity name

The type of entity: dafx- + the agent's name. dafx is the prefix Agent Framework uses for its entities. So there's one name per agent you registered in step 4.

Entity key

Which instance of that type: the session id from create_session(). Name + key together is the entity's address. The 5 at the start of the third group marks a UUID version 5, which is computed from inputs instead of picked at random. That's why replay finds the same session again after a crash.

Last modified

When the entity's state last changed: its last message. Shown in UTC, so 9:11 here is 10:11 local time. The writer is the newest of each trio because it's used until the last section.

Why 12 rows? Every run creates 3 new sessions (Planner, Writer, Editor), and you can see 4 runs: around 6:50, 6:51–6:52, 6:53–6:54 and 9:11 UTC. Entities stay after their orchestration finishes. That's the point of a durable session: you could keep talking to it later. They disappear when the emulator restarts (it keeps state in memory) or, in a real deployment, when the session time-to-live cleans up idle sessions.

    What

    Starts two local services: the Durable Task Scheduler emulator, which stores all durable state, and agentgateway, which forwards model calls to Luna.

    Why

    The emulator is the same scheduler you would use in Azure, so no cloud account is needed. The gateway keeps provider keys and routing out of the app: the code only knows a URL and a model name.

    Needs

    • Docker
    • DTS_TASK_HUB_NAMES listing the hub, or the emulator only creates default
    • agentgateway config with a working Luna route

    The emulator keeps state in memory. Restarting the container wipes past runs, and that also counts as a failure the demo does not recover from. In Azure the scheduler persists state.

    What

    Creates three ordinary Agent Framework agents (Planner, Writer, Editor), each with its own instructions. The middleware appends a line to output/llm_calls.log after every real model call.

    Why

    The agents themselves contain nothing durable. Durability is added when they are hosted (step 4). The log is the proof: a call answered from history never reaches the middleware, so it never appears in the log.

    Needs

    • An OpenAI-compatible endpoint (agentgateway)
    • Chat Completions client: stateless, the durable session supplies the history

    Register everything on the worker

    worker.py · main()
    worker = get_worker()
agent_worker = DurableAIAgentWorker(worker, deployment_mode="isolated_v2")
for agent in create_agents():
    agent_worker.add_agent(agent)          # each agent becomes a durable entity type
worker.add_orchestrator(research_report)
worker.add_activity(save_section)
worker.add_activity(save_report)
worker.start()                             # opens a gRPC stream and waits for work

    What

    Wraps the worker so each agent is hosted as a durable entity. One entity instance is one conversation session. Then registers the orchestrator and the two activities by name, and starts pulling work.

    Why

    The scheduler only hands out work by name. Any worker that registers the same names can run any step of any instance, which is exactly what lets worker #2 continue worker #1's run.

    Needs

    • deployment_mode="isolated_v2": the 1.0 GA release refuses to start without an explicit choice; this one says the task hub belongs to this app alone
    • The same registrations on every worker

    Sends a single request to the scheduler. It records an ExecutionStarted event with the input, queues a work item and returns an instance id straight away.

    Why

    The client never runs any of the work. It can exit right away, and the run keeps going whether or not any worker is up yet.

    Needs

    • The orchestrator name matches a registered one
    • The input is JSON-serialisable and under 1 MB

    Plan the outline

    worker.py · research_report
    orchestrator yields→call Planner entity→Luna→result recorded→orchestrator resumes
    agents = DurableAIAgentOrchestrationContext(context)
planner = agents.get_agent("Planner")
plan_raw = yield planner.run(
    messages=f"Plan a report on: {topic}. Use exactly {n} sections.",
    session=planner.create_session(),
    options={"response_format": Outline})   # Pydantic model → structured output
outline = plan_raw.value

    What

    planner.run() does not call the model here. It returns a durable task that tells the scheduler to send a message to the Planner entity. The orchestrator then yields and stops running. The entity makes the model call, the result is recorded in the history, and the orchestrator is woken up again with it.

    Why

    Every yield is a checkpoint. Results come back through the history, so the scheduler always knows exactly what has finished. The Outline model turns the free-text reply into typed data the loop can rely on.

    Needs

    • Orchestrator code is a generator and deterministic
    • Session ids come from create_session() inside the orchestrator, so they are the same on replay

    Write each section in one durable session

    worker.py · the for loop
    writer_session = writer.create_session()
for i, section in enumerate(outline.sections, start=1):
    status("writing", i - 1, total, section.title)     # custom status for client and dashboard
    resp = yield writer.run(
        messages=f"Report: {outline.title}\nWrite section {i}: ...",
        session=writer_session)                    # same session → remembers earlier sections
    path = yield context.call_activity(save_section, input={...})
    section_texts.append(resp.text)                # rebuilt from history on replay

    What

    For each section: one checkpointed Writer call, then one checkpointed save. All Writer calls share one session, so the Writer entity's state holds the whole conversation so far.

    Why

    A shared session keeps the sections consistent without passing earlier text back in by hand. Two yields per section gives two checkpoints, so a crash loses at most the step that was in progress.

    Needs

    • Entity state under 1 MB. This session is what grows. See payload-limits.md
    • Data the orchestrator uses comes from history, never from disk (section_texts)

    Save each section to disk

    worker.py · save_section
    def save_section(ctx: ActivityContext, data) -> str:
    out_dir = OUTPUT_DIR / ctx.orchestration_id
    path = out_dir / f"{data['index']:02d}-{slug}.md"
    path.write_text(f"## {index}. {title}\n\n{body}\n")   # overwrite: safe to run twice
    return str(path)

    What

    An activity: plain code that does I/O. It writes one Markdown file and returns the path, and the path is recorded in the history.

    Why

    Orchestrators are replayed, so any side effect in them would run again on every replay. Side effects belong in activities, which run once and have their result recorded.

    Needs

    • Idempotent: activities run at least once
    • Shared storage for multiple machines (local disk is fine on one machine)

    The crash

    worker.py · save_section, CRASH_ON_SECTION=3
    section 3 written (recorded)→save_section 3 picked up→os._exit(137)
    crash_on = int(os.getenv("CRASH_ON_SECTION", "0"))
marker = out_dir / ".crashed"
if data["index"] == crash_on and not marker.exists():
    marker.touch()                    # crash only once per instance
    os._exit(137)                     # no cleanup, no finally blocks, like kill -9

    What

    While saving section 3, the worker kills itself instantly. The activity never reports back. The scheduler still holds the work item, locked by a worker that no longer exists.

    Why

    os._exit skips every cleanup handler, the same as an out-of-memory kill or a host restart. The marker file makes sure the second worker doesn't crash too.

    Needs

    • Nothing for recovery. The history already holds the outline and sections 1–3. Only the in-flight save is lost

    What is lost at this moment: one unfinished file write. What is kept: four model calls that cost time and tokens, plus the writer's full conversation.

    Recovery by replay

    scheduler + worker #2
    worker #2 connects→save_section 3 runs again→orchestrator replays plan, s1–s3→Writer section 4
    log = (lambda *a: logger.info(*a)) if not context.is_replaying else (lambda *a: None)
# On replay every `yield` whose result is already in the history returns it immediately:
plan_raw = yield planner.run(...)   # → recorded outline, no model call
resp     = yield writer.run(...)    # → recorded section 1, 2, 3, no model call

    What

    A fresh worker starts. The scheduler hands it the unfinished save_section 3 again, which now succeeds. Then it runs the orchestrator from the top. Every yield with a recorded result returns immediately, until the first step with no result yet: Writer section 4.

    Why

    Rerunning the code against recorded results rebuilds the exact in-memory state (outline, file paths, section texts) without saving any of it separately. is_replaying keeps the logs from printing everything twice.

    Needs

    • Deterministic orchestrator: no clock, random, disk or network inside it
    • The same code version as the run that started (or a versioning strategy)

    Summary and final report

    worker.py · Editor, save_report
    summary = yield editor.run(messages=f"Write the executive summary ...\n\n{full_text}",
                           session=editor.create_session())
report_path = yield context.call_activity(save_report, input={...})

    What

    The Editor gets the full text and writes bullet points. An activity stitches title, summary and sections into report.md. The orchestrator returns a small result, which ends the instance as COMPLETED.

    Why

    The return value is the orchestration output and is stored in the scheduler, so it stays small: just paths and counts. The report itself stays on disk.

    Needs

    • The Editor prompt holds the whole report. Fine at 10 KB, a problem near 1 MB

    Checkpoints and the crash, workflow style

    Unit of progress

    The workflow runs in supersteps: all messages that are ready get delivered, each target node runs once, and their outgoing messages wait for the next superstep. The durable host records each superstep's results and state changes. A section takes two supersteps: Writer, then section_saver.

    What the crash loses

    The section_saver step for section 3. Workflow state is only updated when a step completes, so the retry sees the same snapshot, gets i = 3 again from len(section_files) + 1, and overwrites the same file.

    Needs

    • Every non-agent node is idempotent: it can run twice with the same input and state
    • Workflow state is JSON-serialisable (we store outline.model_dump(), not the model object)
    plans1s2s3save s3 💥 pid 3647600→save s3 agains4s5s6summarypid 3650792

    Measured in run f782b51a… (MODE=workflow, crash on section 3): 8 model calls, the process id changes once, no call repeated. This is the same result as the orchestration version.

    New trade-off: the event log

    When you host the workflow yourself, the extension writes every step's executor_invoked and executor_completed event, with its data, into the orchestration's custom status, so stream_workflow() clients can follow along. That log holds each section's text and keeps growing, and custom status is capped at 1 MB. In this version it fills up before the Writer session does. There's no public switch to turn it off when you host it yourself. Details in docs/payload-limits.md.

    In the dashboard

    Orchestrations

    Runs show as dafx-report_workflow instead of research_report. The custom status is the event log, not our phase object.

    Entities

    Names include the workflow: dafx-report_workflow-Planner, …-Writer, …-Editor. The key is the run's instance id, so all three entities of a run share one key.

    Activities

    One per non-agent node: dafx-report_workflow-intake, …-dispatcher, …-section_saver, …-finisher. They appear as tasks in the run's history.

    Which one to use

    Orchestration

    The flow is easiest to read as code, or you need Durable Task features directly: timers, external events, sub-orchestrations, your own compact progress status.

    Workflow

    You want the flow as a reusable, visualisable graph that also runs without the scheduler (in-process). The extension adds durability without you writing an orchestrator.

    What is different from the earlier versions

    Responses API

    Luna is a reasoning model and rejects tools on Chat Completions (400: Function tools with reasoning_effort are not supported … use /v1/responses). Both agent modes use OpenAIChatClient, the Responses client, with store=False, so the durable session is the only record of the conversation.

    Nobody calls the agent "again"

    In agent mode the orchestrator sends one message and waits for the final answer. In durable-tools it does call the agent once per step, but only to hand back the tool results the model asked for. It never decides what comes next.

    Run id

    Each tool needs to know which run's folder to use. The task text includes run_id: …, and the instructions tell the agent to pass it to every tool. It's simple, but it relies on the model to get it right.

    How durable-tools works

    # the agent only sees declaration-only copies: name, description, schema, no code
FunctionTool(name=t.name, description=t.description, func=None, input_model=t.parameters())

for step in range(1, MAX_STEPS + 1):
    resp = yield author.run(...)                        # exactly one model call (it can't run the tools)
    calls = [c for m in resp.messages for c in m.contents if c.type == "function_call"]
    if not calls: break                                  # the agent decided it's done
    results = yield task.when_all([context.call_activity(run_tool, input=c) for c in calls])
    tool_results = Message(role="tool", contents=[Content.from_function_result(...)])
    # next author.run(messages="", context_messages=[serialize_input_message(tool_results)], ...)

    What

    A generic loop: a model call, then the requested tools as activities, then the results back to the model. It knows nothing about reports. Parallel tool calls run in parallel through when_all. A tool that fails returns its error to the model as the result, so the agent can react.

    Why

    It lifts the tool loop out of the agent and into the orchestrator, where every step is recorded in the history. This is the same structure Dapr Agents uses for its durable agent.

    Needs

    • Tool results sent as context_messages: the durable agent only accepts text as messages
    • serialize_input_message comes from the extension's private _response_utils, so pin the package version
    • A fixed id per step (context_message_ids), so a redelivered message is never stored twice
    • Idempotent tools: an interrupted call runs again

    Earlier failures of this version are visible in the dashboard as two Failed runs. agent_loop 90fa65c5… used Chat Completions with tools (the 400 above). The first tool_loop attempt sent the tool results as messages and got DurableAIAgent only supports text message inputs, which is what led to the context_messages approach.
